| # | 候选流程 | 评估结论 | 理由 |
|---|----------|----------|------|
| A | 给测试文件批量追加日期前缀 | ✅ **适合** | 有界面（文件管理器手动重命名）、无现成批量接口、路径固定、每天重复；仅新建/改名，可逆 |

→ 最终选 **A**：风险最低、完全可逆、最适合用 1 条测试数据练习。

## 2. 我最终选择的流程

**给指定测试目录里的文件批量追加 `YYYY-MM-DD_` 日期前缀**（流程名：`prefix-date`）。

## 3. 它为什么符合"有界面、没接口、路径固定、重复多次"

- **有界面**：日常是在文件管理器里手动逐个改名，是典型的 GUI 重复操作。
- **没接口**：没有现成的批量重命名 API / 导入导出可用（用 shell 是本次自动化手段，不是业务系统既有接口）。
- **路径固定**：操作对象始终是同一个"收件/测试"目录。
- **重复多次**：每当测试截图、日志、文档丢进该目录，都要手动加前缀归档。

## 4. 我如何准备测试环境和安全副本

- 新建专用测试目录 `inbox/`，放入 3 个自建的假测试文件（`alpha.txt` / `beta.log` / `gamma.csv`），模拟待整理内容。
- 先 `cp -r` 整目录到 `inbox_original_backup/`，**原始文件始终不动**，所有操作只在副本上进行。
- 关闭了无关页面，未涉及任何密码、验证码、账号或隐私数据。
- 首次回放只允许放入 **1 条**测试数据（`delta.txt`）。

## 5. Codex 从示范中提炼出的主要步骤

（本次在 WorkBuddy 沙箱中由助手真实执行示范，等价于"录制"——Codex 观察并总结主线）

1. 进入目标测试目录。
2. 遍历目录下每个文件。
3. 对每个文件重命名为 `${DATE}_${原文件名}`（DATE = 当天 `YYYY-MM-DD`）。
4. 逐个回显"原名 -> 新名"。
5. 完成后列出目录确认结果。

示范结果（3 个文件全部成功）：
```
alpha.txt  -> 2026-08-05_alpha.txt
beta.log   -> 2026-08-05_beta.log
gamma.csv  -> 2026-08-05_gamma.csv
```

## 6. 我校对或补充了什么

校对时发现朴素主线有缺陷：**若文件已带日期前缀，会被再次加前缀，变成 `2026-08-05_2026-08-05_x.txt`**。
补充了一道护栏：文件名已以 `YYYY-MM-DD_` 开头时跳过。并把"禁止对唯一原件操作""首次只回放 1 条"明确写入 SOP。

## 7. 第一次单条回放的结果

- 放入 1 条测试数据：`delta.txt`
- 预期：`2026-08-05_delta.txt`
- 实际：`2026-08-05_delta.txt`
- 比对：**✅ 预期 == 实际，回放成功**
- 回放后全量核对：原有 3 个文件未被误伤，目录共 4 个文件，命名一致。

## 8. 我做的一次人工检查或纠正

纠正了"双重前缀"缺陷：在独立的护栏测试中，目录混合了"已带前缀"和"未带前缀"文件，朴素流程会重复加前缀。加入正则护栏 `^[0-9]{4}-[0-9]{2}-[0-9]{2}_` 后：
```
跳过(已带前缀): 2026-08-05_old.txt
加前缀: fresh.txt -> 2026-08-05_fresh.txt
```
结果无双重前缀，纠正生效。

## 9. 这个流程的人工确认点和异常停止条件

- **人工确认点**：回放前确认"只放入了 1 条测试数据"；重命名后确认目录全量无误伤。
- **异常停止条件**：
  - 文件名已含日期却仍被要求再次加前缀（护栏失效）。
  - 目录出现非预期文件（误放入真实资料）。
  - 重命名报错（权限/同名冲突）。
  - 任何"保存/发送/上传/删除/发布"动作前。
