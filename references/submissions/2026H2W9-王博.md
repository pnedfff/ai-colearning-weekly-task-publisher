## 2. 我的工作流：浏览器 → 清单 → 预检 → 得到大脑 → 核验

按 `dedao-course-to-getnote` 的定义，这五步的输入、输出和边界分别是：

| 步骤 | 输入 | 输出 | 边界（关键） |
| --- | --- | --- | --- |
| ① 浏览器发现 | 已登录的课程页 | `order_num` / `title` / `enid` / 发布状态 | 只取安全字段，在浏览器执行环境内裁剪后再回传，不把整份响应带入对话 |
| ② 本地清单 | 上一步字段 | `course-articles.json` | 按 enid 和规范网址去重，只留本机，不进仓库 |
| ③ 预检 dry-run | 清单 | 已存在 / 待新增 / 已发布三个数 | 只查重不写入；网址扫描默认 10 页，`--url-scan-pages 0` 才全量 |
| ④ 得到大脑同步 | 预检后的 URL | `getnote save` 任务 | 并发上限 3，重试 1 次，状态文件断点续传 |
| ⑤ 核验 | 笔记 ID | 真实性判定 | 不能以「退出码 0」当成功，要核对 URL、标题、正文长度 ≥100 字 |

我在本机完成了这条链路的**环境搭建与脚本验证**，但没有拿到课程数据，所以②③④⑤ 均无实际产出数字。

## 7. 我遇到的真实阻塞及处理方式

**阻塞：账号不是得到大脑会员，OpenAPI 整体不可用。**

排查过程（每一步都有回显为证，不是猜测）：

1. 安装 CLI：`npm install -g @getnote/cli@latest` → 成功，v1.5.10，命令已进 PATH。
2. 授权：`getnote auth login` → 浏览器 OAuth 成功，`auth status` 返回 `Authenticated`，API Key 有效期至 2027-09-06。
3. 诊断：`getnote doctor -o json` → `diagnostics_completed: true`，`local_ready: true`，但 `ready: false`，原因：
   `API error 10201: not_member: OpenAPI 仅对会员开放`
4. 只读验证：`getnote notes --limit 1 -o json` → 同样返回 `10201 not_member`，并给出 `membership_url`。

**结论：本地环境没问题（`local_ready: true`），CLI 和 Skill 都没装错，纯粹是账号权限挡住。**

处理方式：**不绕过**。我没有去找任何破解、共享 Key 或第三方接口，也没有伪造数量。按 W9 完成标准里「如实记录登录、购买、授权等真实阻塞」这一条，把过程写成本报告打卡。

如果后续开通会员，恢复路径很清晰：从浏览器打开任一已购课程文章 → 生成清单 → `--dry-run` 预检 → 确认后同步。清单、状态和 Skill 都已在本机就位，不需要重做环境。

## 8. 我理解的「Skill 串联」

不是把几个提示词串起来跑一遍，而是**每一步都产出可被下一步校验的输入**：

- 浏览器只负责「发现网址」，不负责取正文——所以它对模型的输出必须是裁剪过的安全字段，而不是整份响应；
- 清单是「可检查的中间产物」，所以它能被 dry-run 独立验证，也能被断点续传复用；
- 得到大脑只接收 URL 自行提取——所以本地永远不落课程全文，版权和泄露风险从架构上就被切断；
- 最后一步必须**反查落库结果**（URL 是否匹配、正文长度是否够），而不是相信上一步的返回码。

一句话：**上一步的产出必须是下一步可验证的输入，并且每一步都有明确的「不做什么」边界。** 这周我虽然没跑到数据，但把这四层的边界读清楚了——脚本里 URL 白名单校验、并发硬上限 3、原子写状态文件、正文长度 ≥100 字判定，都是这个思路的落地。

## 9. 下次可复用的一条规则

**先验证外部依赖的「权限」，再验证「功能」。**

以前我排查工具问题会先怀疑装没装对、版本对不对。这次 `doctor` 直接给了 `local_ready: true` + `not_member`，如果没看这一层，我很可能反复重装 CLI、查 PATH、怀疑是 Windows 环境问题，白白耗掉一小时。

以后接任何带 OpenAPI/配额/会员门槛的服务，第一步就跑它的诊断命令，先确认「我有没有资格用」，再确认「我装得对不对」。这次从安装到定位阻塞总共不到 15 分钟，就是靠这个顺序。
